## Findings

### The last pod Ready is the Strimzi entity operator, not ingest
- **The claim:** ingest is the last pod to go Ready.
- **The data:** in all three cold runs, `flotilla-entity-operator` goes Ready 10–12 s after
  ingest. Strimzi creates it only after Kafka is Ready.
- **Effect:** the "first pod → last pod Ready" spans (395, 390, 401 s) end on the entity
  operator. Ingest is the last of the four service pods.

### `R0-pods.json` is not from any of the six runs
- **What it is:** an 18:48–18:55Z run with images tagged `sha-c4e640e-dirty-04ed5364`
  (uncommitted work on top of `1ff5212`).
- **What happened to cold run 1's JSON:** it was overwritten in the clone by the runs after
  it (`demo/R0.sh:66` rewrites the file on every run).
- **What survives:** cold run 1's Pod Ready table in its log. That table matches the JSON
  exactly wherever both exist.

### Image size: the two measures differ by a constant 1.06 MB (3.7–6.5%)
- **The gap:** `crictl` reports 1,058,822–1,058,831 bytes more than `docker image inspect`
  for every image. The four images share 13 base layers and differ only in the app layer.
- **What each tool counts:** `crictl` reports 33,197–33,206 bytes less than
  `docker save | wc -c` (`docker-save-bytes-abeb343.txt`). So it counts the uncompressed
  layer tars that `kind load` imported. `docker image inspect` counts unpacked file bytes.
